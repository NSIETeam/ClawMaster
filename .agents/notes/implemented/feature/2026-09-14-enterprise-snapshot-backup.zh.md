# Agent Note: 导出已校验的企业快照

Status: implemented

[English](2026-09-14-enterprise-snapshot-backup.md) | 中文

## 问题

本机 CRM/ERP 存储已有持久化和审计，但面板没有提供用户控制的备份操作，尽管其中保存了业务记录。

## 决策

两个面板在同一 SQLite 读事务中导出通过 schema 校验的企业快照和命令回执，保存为带日期的 JSON。导入的回执内容必须与审计记录匹配。面板预览数量，并要求明确确认目标数据库的 revision 和恢复代次 generation。Host 在写锁内检查两个值，原子替换业务记录和回执，并递增目标数据库的代次，不导入备份中的计数。Schema 2 向 schema 1 存储增加该计数；缺少此字段的旧协议请求仅属于代次零。

命令准备和提交均先检查恢复代次，再判断幂等重放。待处理审批和旧页面不会因导入 revision 重复而重新获得修改权限。恢复 HTTP 处理器参与路由所有者的请求排空，并在读取请求体后再次检查取消。浏览器串行处理恢复和命令，使旧读取失效，保留服务端冲突分类，并在恢复响应不确定时要求刷新权威数据。

CRM 和 ERP 表单及确认保留打开时观察到的恢复代次。刷新或修改保留的草稿不会授权它覆盖恢复后的记录。被拒绝的旧表单保留输入，并提示用户复制需要的内容、取消并基于当前记录重新打开。

## Alternatives considered

**从浏览器复制 SQLite 文件。** 浏览器代码无法安全访问 Host 数据库路径，而且会绕过已认证的快照约定。

**导入时自动恢复。** 隐式替换可能破坏较新的记录；因此存储原语要求独立复核流程、版本检查和格式检查。

**仅使用导入的 revision。** 恢复较旧版本会使旧请求重新有效。目标数据库自己的代次既保留审计 revision，又使这些请求失效。

## Consequences

操作员可以恢复企业记录和审计回执，而不会授权来自数据库旧代次的请求。此备份仅覆盖企业数据，不是完整 DSH 主目录导出。恢复响应丢失后需要刷新，再继续修改；待确认的命令请求保留既有显式幂等重试流程。

## Verification

存储测试覆盖重复 revision、旧请求、重新打开后的代次持久化、schema 迁移、回执不匹配和事务失败回滚。客户端测试覆盖延迟读取、重叠修改、响应丢失和冲突；渲染面板测试覆盖明确确认及结果不确定后的刷新。工具测试拒绝恢复后才结束的审批和旧分页代次。Loader 业务流程场景将代次记入模型可见命令回执，并校验 JSONL 回放。
