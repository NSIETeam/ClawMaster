# Agent Note：原生 RPA 写操作必须经过桌面 broker

Status: implemented

[English](2026-09-18-clawmaster-rpa-native-approval-broker.md) | 中文

## 问题

独立 RPA 助手收到的非空批准编号由调用方提供，无法证明 DSH 确实批准了操作。

## 决策

Host 通过继承的双向 stdio 管道发送只读调用和已批准的写请求。Tauri Rust 主进程拒绝读通道上的写操作；审批通道上的写操作须通过 DSH 审批、原生确认、工具分类、调用编号、规范参数哈希和批准摘要校验后才会派发。助手 CLI 的写调用和原始 input 均会被拒绝。RPA 组件启动时会发送新的 hello；即使另一个提供方先消费了启动帧，Host 也能重新取得 ready 回复。WSL 会明确回复不支持原生 RPA，但仍保留独立的操作系统凭据 broker。

桌面进程将 broker 视为可选组件。broker 缺失只会禁用原生 RPA 写操作，不会阻止 Host 或其他桌面功能启动。

broker 会在 Host 进程存续期间，按规范化后的配置目录复用一个原生 RPA 控制器。浏览器成功启动后，后续调用仍可继续操作；Host 退出并释放控制器时，会终止由它启动的浏览器。

## 考虑过的替代方案

**信任助手参数中的 `approvalId`** 被拒绝，因为调用方无需访问 DSH 批准服务就能伪造该值。

**回环 HTTP、环境变量、argv token 或临时授权文件** 被拒绝，因为它们会让授权凭据离开父子进程管道，并增加可被助手重复使用的凭据。

**只使用 DSH 批准提示** 被拒绝，因为 Rust 进程无法在发出原生输入前独立确认用户意图。

## 后果

每次桌面写操作都需要用户做出两次决定。桌面 broker 可用时，状态读取与写操作复用同一 Host 控制器，避免其它进程重新打开已加锁的状态数据库。只有 broker 在派发前明确报告不支持时，才允许退回助手；传输故障不会把同一调用交给另一个进程重试。请求超时会向正在执行的原生调用发送取消帧；`rpa_wait` 会响应取消，已派发的原生操作则可能继续完成，并报告结果未知。无状态能力和定义查询无需打开状态数据库。
