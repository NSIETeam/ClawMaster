# Agent Note: Obsidian 风格知识工作台

Status: implemented

[English](2026-09-21-obsidian-style-knowledge-workspaces.md) | 中文

## Problem

笔记客户端把导航、编辑和相关信息放在同一个纵向流程中，压缩了文档的可读区域，也让上下文难以浏览。Graph Memory 只展示数量与排序后的关系对，没有绘制已经存储的图，因此用户无法在侧栏探索拓扑、邻域或关系依据。每次刷新还会读取并解析全部笔记，即使笔记库没有变化。

## Decision

笔记使用受 Obsidian 信息架构启发的桌面知识工作台，但不引入 Obsidian 的代码或资产。活动栏与笔记库树负责导航，中央文档区负责编辑和预览，独立检查器集中展示批注、反向链接、标签与待审建议。容器变窄时，容器查询依次移除次要区域，同时保留文档以及既有的修订、草稿和批准行为。

Graph Memory 把通过校验的快照渲染为交互式 SVG 网络。确定且有界的力导向计算负责节点位置，语义颜色区分节点类型；客户端支持搜索高亮、节点类型筛选、全局与一跳局部范围、平移、缩放、选择以及关系依据检查器。画布在当前范围内最多绘制连接度最高的 140 个节点；这个上限只约束呈现，不改变存储快照或检索路径。

Graph Memory 存储单元还会保留通过校验的源文档记录。刷新时，系统会把每条 Notes 列表项与已存储的路径、笔记库、字节大小和修改时间进行比较。未变化的记录会直接复用；只有发生变化或新增的笔记会在重建完整派生图之前重新读取。笔记被删除时，对应缓存记录也会删除。这些记录属于可重建索引数据，不是用户内容。

两个客户端均保留现有宿主、路由、修订和批准约定。该实现不增加可视化框架、专有笔记格式或第二套可由用户编辑的图数据表示。

## Alternatives considered

**保留纵向堆叠的笔记面板，只调整排版。** 仅调整排版无法分离导航、文档工作和审阅上下文，文档仍会与所有辅助区争夺纵向空间。

**继续把 Graph Memory 展示为排序列表。** 列表可以暴露单条关系，却会隐藏聚类、枢纽和邻域结构，而这些正是存储图谱的主要价值。

**增加通用图可视化依赖。** 已交付的交互集合足够由 SVG 和 React 状态实现。不增加客户端依赖可以让 bundle 所有权和渲染行为保持局部，代价是使用有界的自定义布局，而不是完整物理引擎。

**绘制索引中的所有节点。** 无界 SVG 图在大型索引上会降低交互流畅度与标签可读性。按连接度选择呈现可以保留关联最强的结构；完整图仍供检索使用，也可以通过筛选与局部模式缩小范围。

**只存储完整图快照。** 每次刷新都从源文件重新构建虽然简单，却会对每篇未变化的笔记重复执行读取和解析。按文档保存的可重建记录既保持源文件所有权，也避免了这些重复工作。

**把元数据相等视为内容保证。** 在少见的外部改写情况下，文件系统可能保留原有元数据。Graph Memory 只用元数据选择候选文件；显式删除索引仍会触发完整源文件重建，也是恢复路径。

## Consequences

笔记获得清晰的桌面区域和易读的中央文档，但在窄容器中会先隐藏检查器，再隐藏笔记库树。图拓扑可以直接探索，每一条选中关系都保留存储的依据。每当可见节点集合变化时，确定性布局都会消耗 CPU，因此呈现上限属于界面行为的一部分。

普通刷新会避免读取未变化的笔记，而发生变化的笔记是唯一需要重新解析的笔记。源文档收集完成后，实现仍会重建全局相似度、聚类和原子快照；它不宣称已经支持 SQLite FTS5、陈旧代际分页、恢复历史、同步或旧 `memory.md` 迁移。这些更大的改动仍由[知识库 v2 提案](../../proposed/architecture/2026-09-22-obsidian-compatible-knowledge-vault-v2.zh.md)负责。
