# Agent Note：组件健康只提供给操作者自己的桌面

Status: implemented

[English](2026-09-22-local-component-health.md) | 中文

## 问题

首页报告了应用连接、模型证据、定时执行器与业务任务，却没有报告 Host 自身的组件，于是 Host 禁用的插件对使用者是看不见的。事实是存在的，但只到达模型：`runtime_status` 与已记录的运行时上下文带有组件清单和被禁用插件列表，而浏览器没有任何路由能读到它们。新增一条路由会立刻遇到仓库里对其它产品路由已经回答过的问题——它由哪项权限把关——而这里的答案并不显然：十个 `GovernanceAction` 覆盖记录、审计、任务、附件与工作区，没有一个描述「读取 Host 自身运行时」。

## 决策

`frontends/dsh/src/runtime-health-host.ts` 提供 `GET /api/clawmaster/runtime`，并且只在 `GovernanceAccess.mode` 为 `local` 时提供，否则拒绝。共享 Host 服务的是并非该机操作者的身份，所以它的组件清单不进浏览器；客户端把这种拒绝渲染为「未观测」，而不是健康。该路由自己不读任何文件：`mountRuntimeHealth` 把观测作为注入的读取器接收，由 `host.ts` 传入 `observeRuntime(process.env.CLAWMASTER_RUNTIME_STATE)`，这样路由自己的测试不必解析工作区包。

载荷包含观测时间、可用性与原因、`release`/`development` 模式、组件数量，以及本机禁用掉的插件名。它不含文件系统路径、摘要、PID、端口或凭据。`frontends/dsh/src/runtime-health-client.ts` 在首页载入时读一次、刷新时再读一次，并把所有失败——被拒绝、不可达、格式不符——一律报告为未观测。

## 影响

组件健康成为首页的第五层：未观测或被拒绝是中性态，被禁用的插件会在折叠详情上方那一行里点名该层，详情行给出数量。这是这一层能支撑的东西——Host 对自己载入了什么的记录——而不是逐组件的功能检查，这条限制也写在行内文本里。

该路由只在本机模式提供，因此企业部署看到的是「未观测」，而不是服务端的组件列表。在那里启用它需要一个尚不存在的权限动作，而选定它就等于决定哪些角色可以读取 Host 事实；这个决定仍未做出。

组件清单本来就已经对模型可见（`runtime_status` 与已记录的运行时上下文都不带治理校验）。这条路由没有把这种披露扩大到共享 Host，但它确实让浏览器读到了模型读的同一份记录，所以日后改动 `observeRuntime` 的披露范围会同时影响两者。
