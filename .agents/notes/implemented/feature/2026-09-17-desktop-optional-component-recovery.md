# Agent Note: Desktop Optional Component Recovery

Status: implemented

English | [中文](2026-09-17-desktop-optional-component-recovery.zh.md)

## Problem

One missing or failing feature component could prevent the desktop Host from starting, making unrelated ClawMaster features unavailable.

## Decision

ClawMaster keeps the core desktop usable when a feature bundle is unavailable. Profile preparation validates optional patch files, presets, and component-owned storage per bundle; it omits an invalid bundle and logs the failure. Missing profile dependencies classified by `optionalClientPackages` do not trigger a repair of the whole Web profile; native startup recognizes the stable desktop optional package set for legacy Web profiles before the preload can migrate them. Host recovery recognizes import, apply, and pending-loader diagnostics, then retries after disabling only allowlisted feature entries. If updater maintenance is missing or fails, startup preserves all updater journals, logs whether recovery is pending or unreadable, and continues to the core Host; the update remains unapplied until maintenance can resume. Browser feature clients have isolated startup scripts, and optionality propagates to every non-core consumer of optional dynamic-module or service-injection dependencies; removing an optional cyclic adapter retains its optional identity for deeper consumers. Required clients activate before the UI opens, while optional activation continues in the background so a stalled feature cannot block the core page. Optional prefetch is excluded from the required startup stage, and failed optional fibers are removed when their activation settles. Missing or malformed authored source maps fall back to identity maps and do not disable their client. Malformed tool schemas are quarantined per tool so other registered tools remain available. The main frontend, desktop policy, Guard, permission, and approval entries remain required.

## Alternatives considered

Disabling every loader entry after a startup error was rejected because it could turn a broken or missing security component into an apparently successful launch. Requiring every bundled feature package to validate before profile creation was rejected because a missing Notes, Office, connector, or updater bundle should not prevent the rest of ClawMaster from opening.

## Consequences

Unavailable optional components do not appear in the active desktop profile until a later launch can validate them. Missing packages listed as optional client dependencies are not reinstalled as a prerequisite for opening the core Host; the desktop keeps the full optional classification in the profile, and native startup also recognizes legacy Web profiles where the old launcher already removed optional bundle rows. Required dependencies still use the normal repair path. Invalid routing presets do not replace user files or stop other features; presets from a bundle rejected during Loader composition cannot disable another bundle. A conflicting IM workspace disables IM while preserving the conflicting path. An optional plugin that fails during activation is disabled for the recovery launch, and the desktop shell reports its loader id. Per-platform installed acceptance must verify that the shell stays open, the affected feature reports unavailable, and core session use plus unrelated features continue. Browser core bundles remain in separate combo batches from optional clients. Malformed tool schemas cannot poison model requests or dispatch, while healthy tools remain callable. Adding a desktop feature requires an explicit decision about optionality and, when startup recovery is appropriate, its loader id must be added to the Rust allowlist. Core application and security entries remain fail-closed.

## Verification

`desktop-defaults.test.mjs` verifies that missing, wrong-version, malformed-patch, preset-conflict, and component-storage-conflict cases omit only their optional bundles, while a missing frontend bundle still fails. Rust profile tests verify that current optional metadata and legacy Web dependencies suppress repair for missing feature packages even when prior versions removed all optional bundle rows, while required dependencies still schedule repair. They also verify that excluded components retain their optional classification and that a Loader-rejected bundle cannot remove the healthy updater. Component maintenance tests verify that missing or failed helpers permit startup with no update, a staged update, or unreadable recovery state; pending and unreadable journal bytes remain unchanged. Client module and boot tests verify isolated optional batches, transitive optionality for dynamic-module consumers, and removal of failed optional rows while core boot succeeds. Tool tests verify malformed schemas are excluded from Native projection, direct dispatch, and PTC bindings while healthy tools remain callable. Supervisor tests verify that optional integrations can be disabled while frontend, Guard, sandbox, approval, permission, and unknown entries cannot. Installed-platform recovery and the user-visible status for each disabled feature remain part of desktop acceptance.
