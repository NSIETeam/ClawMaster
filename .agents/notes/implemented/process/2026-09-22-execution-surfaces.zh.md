# Agent Note: 让每个执行面说出它的门禁或它的缺口

Status: implemented

[English](2026-09-22-execution-surfaces.md) | 中文

## 问题

产品能以许多方式改动操作者的机器——写文件、跑 shell 命令、保存 Office 文档、写企业记录、驱动桌面、接受更新——而每一种改动由不同的模块把关。没有任何地方把它们列在一起，于是"某个面是否受管"只能靠逐个模块去读来回答。一个尚未被审视的面，看起来与一个无人看守的面完全一样；而门禁位于本检出之外的某个组件时，那个面看起来就像根本没有门禁。

## 决定

`apps/desktop-tauri/execution-surfaces.json` 把每个执行面记为一条条目：它能改动什么（`surface`）、拒绝它的模块（`enforcer`）、所行使权限的来源（`authorization`）、强制机制（`mechanism`）、演练它的测试（`evidence`），以及 `status`。

`authorization` 要么是仓库内路径，要么是显式的 `{"external": …}` 供给方，因为有些门禁由本检出不含的组件作出：Office 编辑器的保存实现与更新器的签名信任根都由外部提供。

`apps/desktop-tauri/scripts/execution-surfaces.mjs` 将该清单与实际检出核对。`status` 有三个取值。`enforced` 要求给出强制者、授权来源、闭集内的机制，以及至少一条证据路径。`unenforced` 要求写明理由，并禁止再给出强制者或机制。`unclassified` 要求写明理由，说明本清单尚未确立什么。路径缺失、为绝对路径或为空都会失败；重复 id 失败；未知的状态、机制或授权形式失败。

第三个状态正是这个设计的要点。只提供 `enforced` 与 `unenforced` 两个取值的清单，会迫使我们对每个尚未审视的面去猜，而猜出来的结果读起来就像一个答案。

## 后果

随附的清单列出八个门禁与五个缺口。缺口逐个写明，因为它们是**不同的**缺口：仅宿主插件会在没有请求、没有审批的情况下激活，因为那个激活分支排在审批代码块之前；MCP 工具调用没有任何准入判定，于是「选择哪些服务器」的那次挂载与「调用本身」构成同一条无人看守的接缝；出网没有任何目标白名单，唯一存在的拒绝只覆盖一个工具，且检查的是地址类别而不是许可主机集合；模型写的代码在工作线程里被约束，却没有任何审批把关，而运行时自己的模块把那层约束记为 containment 而非门禁；用户层 harness 配置的写入没有任何门禁。

产品新增一个执行面却未在此登记，是检测不到的。清单只保证它列出的每个面都被交代清楚，仅此而已。

`enforced` 断言的是门禁存在，而不是门禁足够。校验器解析路径与字段形式；它不判断条目所写的机制是否真的拦住了它声称要拦住的改动。该判断属于评审，这也正是能力台账为自己的证据路径记录的同一条边界。

要求给出证据路径，能让"有门禁但无测试"变得可见，因此部分条目给出的是测试而非调用同一段代码的工作流步骤。
