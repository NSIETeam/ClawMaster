# Agent Note: 让每条产品承诺都能落到代码与证据上

Status: implemented

[English](2026-09-22-capability-ledger.md) | 中文

## 问题

产品承诺散落在各 README 的散文里，没有任何东西把一条承诺与交付它的代码、或守住它的测试连起来。由此产生两种失败：某个能力的测试被删除、改名或从未写过时，它读起来仍像受支持；而一个从未验证过的能力看起来与已验证的完全一样，因为证据的缺失在评审者会去看的任何地方都没有留下痕迹。

## 决定

`apps/desktop-tauri/capability-ledger.json` 把每条承诺记为一条条目：承诺本身、陈述它的 README 或模块契约（`source`）、交付它的代码（`code`）、守住它的证据（`evidence`）、该承诺被断言支持的平台（`platforms`），以及 `status`。

`requires` 写明证据在检出之外还需要什么——一个环境变量、一个已安装的浏览器、一个签名身份——这样无法复现该次运行的评分者会知道缺的是什么，而不是把该条目读成坏掉了。

`apps/desktop-tauri/scripts/capability-ledger.mjs` 将该台账与实际检出核对。`source`、`code`、`evidence` 中的路径缺失、为绝对路径或为空都会失败。没有 `code` 的条目失败。重复 id 失败，因为无法无歧义阅读的承诺无法被审计。`KNOWN_PLATFORMS` 之外的平台失败，因此未经测量的平台不会因笔误而被声称支持。`requires` 若不是一串非空字符串则失败，因此前置条件读起来是一串事项而不是一句话。`verified` 条目没有证据即失败：宣传一个能力必须有证据。`unevidenced` 条目没有 `reason` 即失败：记录缺口是允许的，对它保持沉默则不是。`unevidenced` 条目可以完全省略 `evidence`，因为一个没有证据的能力没有任何路径可写；而带证据的条目仍必须把它写成路径列表。

台账是"声称了什么"的载体；校验器让这个声称具备代价。因此新增一条承诺，就意味着补上它的代码路径、证据路径，或一条说明为何没有证据的明确理由。

## 考虑过的替代方案

**继续只在 README 文字中描述产品承诺，并依赖人工评审。** Issue 和 PR 记录指出，承诺与交付代码、持续维护的证据之间没有关联，过期声明会与已验证能力无法区分；因此台账把缺少证据显式记录出来。

## 后果

校验器验证的是证据**存在**，而不是它**通过**，也不是它**覆盖**了该承诺。一个不再演练该能力的测试，其路径仍然满足校验，因此当证据被改作他用而非删除时，台账必须同步修订。这个限制是刻意的：判断某个测试是否仍然覆盖某条承诺属于评审判断，而一个靠猜的机械门禁比一个明说自己检查什么的门禁更糟。

平台声明是关于测试的断言，不是测量结果。台账把"已演练"与"策略覆盖"分开：条目会在能力确实于该平台演练过之后才列出该平台，因此多数条目只写 `macos-arm64`；而外壳配置、验收矩阵所强制的签名策略、以及添加发布证据的步骤则列出三个桌面平台，因为这些声明针对的是已发布配置与策略，而不是在每个平台上的一次运行。台账正是让未演练的平台保持可见、而不是被暗示为对等的地方。

有两条条目专门用来记录发布链**没有**的东西。macOS 通道用 ad-hoc 身份签名，并用一种 ad-hoc 签名同样能通过的校验方式去验证它；而同通道据以评分的验收策略要求操作系统发布者签名——流水线与它自己的策略互相矛盾。另外，源码树里引不到任何验收结果：契约与校验器已入库，清单从仓库之外送入，而验收目录里只有它的 README。两条都写明各自涉及的平台集合，且都不带证据路径——这正是 `unevidenced` 条目被允许省略它的原因。

`requires` 写明的是校验器能读到、却无法安装或验证的前置条件。一条证据若需要打过补丁的包和一个已安装的浏览器，那么只有两者都在位时它才可复现，因此因缺少其中任一而失败的运行属于前置条件缺失，而不是能力失败。这个区分写在条目里、紧挨证据路径，因为校验器无法作出这个区分。
