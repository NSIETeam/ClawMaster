# Agent Note: 企业责任历史在恢复后保留

Status: implemented

[English](2026-09-16-enterprise-responsibility-history.md) | 中文

## Problem

业务备份会替换记录及其按修订编号保存的前后审计。若将其作为唯一的责任日志，恢复备份时就会删除其间写入的证据。

## Decision

SQLite schema 3 在恢复载荷以外维护仅追加的责任表。成功写入与责任条目共用业务事务。恢复记录保留备份摘要和恢复前后的修订/代次；独立回执让响应丢失后的显式恢复重试具有幂等性。恢复失败还会标记校验、授权、修订检查、应用或提交阶段。失败、拒绝和取消操作分别记录结果。已认证的授权和任务消费者在身份解析后记录未成功的尝试，包括审批期间撤权。每次尝试只记录操作/命令元数据和固定原因码；请求正文、搜索文本和异常消息不进入责任历史。缺失、未绑定或来自其他组织的身份不会被归为真人。请求 JSON 不能指定操作者或审批字段。HTTP 标识已认证的本机设备操作者；工具标识所属 Session 和调用。企业审批元数据包含授权方签发的审批编号与审批人编号；本地 DSH 一次性审批只记录 `allowed-once` 结果，没有持久审批人身份或审批编号。旧记录中未标明来源的审批对象会保留为未验证的历史元数据。已有业务历史导入时标记操作者未知。

责任历史读取者迭代 SQLite 行，在配置的条数和编码后响应字节预算内返回完整记录。同一读取者按 HTTP JSON 或完整 DSH 结构化值与渲染文本信封计算字节。排他序列游标继续筛选后的仅追加历史；单条过大时在对应游标报错，不丢弃记录，也不返回空的续读页。已有记录和哈希保持不变，提高预算后可以读取该记录。HTTP 消费者在检查当前审计授权之后执行这些限制。

已发布的请求、快照与备份类型保留恢复代次及命令回执。两个模型工具输入 schema 都暴露 HTTP／领域解析器使用的代次；恢复后重新审阅的请求可以在新代次继续执行，过期命令与分页仍会被拒绝。

[业务备份决策](../feature/2026-09-14-enterprise-snapshot-backup.zh.md) 继续定义可移植业务快照和精确库存恢复。责任历史独立保存，该操作既不会替换它，也不会导出它。

表结构变更和版本标记与组织准入、历史校验共用一个事务。若在组织检查前提交 generation 列，被拒绝的 schema 1 数据库就会仍标记为 schema 1，却已存在该列，导致重试失败。拒绝操作保留原有结构和记录，以便按有效的本地模式重试。

## Alternatives considered

**把责任放在被恢复的业务审计中。** 替换该表必然丢失备份之后变更的证据。

**独立的仅追加文件。** 文件追加不能与 SQLite 修改原子提交。共享数据库事务可防止业务变更成功却没有成功记录。

## Consequences

哈希校验检测本地不一致，不能阻止可替换整个数据库的恶意机器管理员。企业留存仍需独立控制的归档。明确的保留策略实现前，历史会持续增长。迁移不会编造旧身份。本地设备标签不能代表企业成员。桌面 Host 无法独立观察外部成员和策略变更；企业级策略变更审计需要授权方提供经过认证的事件流。治理测试覆盖恢复连续性、响应丢失重试、事务失败及阶段、伪造操作者字段、审计写入失败回滚、旧版本导入和哈希链损坏。A→B→恢复回归在重开数据库后仍保留 B 的操作者与审批事实，以及恢复操作者、独立审批人、备份摘要和恢复前后的代次/修订；完全相同的恢复重试不会新增条目。任务派发结果关联持久化的开始命令、任务修订、DSH 请求和 Session 编号；不确定结果可在同一请求编号下追加一个最终事实，完全相同的重试返回已记录事实。真实组织身份提供者与桌面业务验收仍是独立的集成工作。
