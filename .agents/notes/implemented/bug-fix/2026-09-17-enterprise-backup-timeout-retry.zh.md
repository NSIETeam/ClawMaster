# Agent Note：企业备份超时重试

状态：已实现

[English](2026-09-17-enterprise-backup-timeout-retry.md) | 中文

## 问题

上传超时后，接口虽然返回了拒绝响应，请求处理器仍可能等待发送端尚未完成的流读取，并继续占用备份准入名额。立即重试时，错误请求会先得到 `storage_unavailable`，而不是进入请求校验。

## 决策

请求中止时，让当前请求体读取与中止信号竞速，以便路由及时结束并释放操作准入。发送拒绝响应前不取消由 HTTP 传输层拥有的请求体。若仍有传输读取未完成，则保留 reader lock，等该读取结束后再释放。这样既保留响应载体，也允许后续请求继续处理。

## 考虑过的替代方案

**一直占用操作准入名额，直到请求体读取结束。** 发送端停滞可能让该名额无限期无法释放，阻止后续有效请求进入校验。

**返回拒绝前取消由 HTTP 拥有的请求体。** 请求体归 HTTP 载体所有；在写入响应前取消可能破坏响应。让读取与中止信号竞速，可以在处理器释放准入名额的同时，让未决传输读取继续由原有所有者收尾。

## 后果

超时处理区分了处理器生命周期和传输读取的结束时间：中止后可以释放存储和准入名额，但 reader 要等载体完成未决读取后才能解锁。回归测试确认空闲上传超时后立即提交错误请求会得到 `invalid_request`，且销毁期间的 reader lock 会保留到未决读取结束。
