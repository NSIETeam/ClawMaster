# Agent Note: check order and inventory grants in one policy snapshot

Status: implemented

[English](2026-09-17-order-submit-policy-snapshot.md) | 中文

## Problem

提交订单会修改订单及其引用的每条库存记录。分开执行异步权限检查可能观察到不同版本的成员策略；审批等待期间，任何受影响资源的授权都可能被撤销。

## Decision

`GovernanceCaller.checkMany` 只读取一次执行者和委派者的成员权限，并要求同一策略快照允许全部请求资源。HTTP 和 DSH 工具提交订单后会调用它，一次检查订单和所有关联库存项目。返回身份携带该快照的策略版本，并保留此命令已消费的审批凭据。权威审批者通过验证后，即使后续权限检查拒绝，责任记录也会保留该审批凭据；每次新审批开始时都会清除上一次尝试的凭据。

审批者授权检查与执行者检查共用相同的精确、家族通配符和全局资源匹配逻辑。家族授权仍仅限其资源家族。

## Alternatives considered

- **分别检查每项库存资源并选择最高策略版本。** 各结果可能来自不同策略状态，汇总出的版本会暗示一项从未真实存在过的组合授权。
- **依赖审批前的资源检查。** DSH 审批或企业审批等待期间，成员授权可能变化。
- **拒绝家族范围的审批者授权。** 这与执行者可用的资源授权格式矛盾，使配置等价的权限表现不同。

## Verification

治理测试覆盖 HTTP 权威审批和 DSH 工具审批等待期间撤销库存授权、最终成员权限读取期间撤销订单授权、保留有效审批并更新策略版本，以及家族范围审批者授权。原实现会允许库存授权已撤销的 HTTP 与最终快照场景，并拒绝家族范围审批；更新后的用例通过。

## Consequences

- 多资源判断使用同一成员权限快照，不再拼接多次读取的结果。
- 审批后的权限检查观察到撤权时，事务不会提交。
- 消费审批后发生的拒绝会在责任历史中保留已验证的审批引用，之后失败的尝试不会继承它。
- 权限检查结束后、SQLite 提交前，权威服务仍可能改变授权；消除该时间间隙需要权威服务与业务写入共用事务授权协议。
